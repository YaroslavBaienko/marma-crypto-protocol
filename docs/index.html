Q1. Why is Marma-256 needed if embedded PAdES /ByteRange already covers the PDF?
When an embedded PAdES file stays untouched, /ByteRange indeed covers all bytes outside /Contents. Marma-256 addresses 4 real-world workflow gaps where /ByteRange is absent, stripped, or bypassed:
1. Detached .p7s / CAdES workflows: The PDF itself has no /ByteRange, only a decorative visual stamp carrying 0 bits of cryptography (while state agencies often reject PDFs lacking a visible page stamp).
2. DMS Flattening (Print-to-PDF): Corporate DMS/archival pipelines strip binary /Contents containers, whereas vector paths (q ... m l h S Q) survive with a 9.207 µpt margin and retain all 256 bits of $V = \text{SHA-256}(r \parallel s)$.
3. Incremental "Shadow" Appends: Binds the canonicalized visible text stream across the whole document to the 9-triangle geometry.
4. Zero-Crosstalk Canary Leak Tracing (D5.ay): 27th orthogonal channel encodes a 10-bit recipient beacon ($I(V; w_c)=0$).
Q2. Does this invent custom signature cryptography, and is it Post-Quantum (NIST PQC) ready?
No custom signature primitive: Non-repudiation relies strictly on standard asymmetric algorithms (DSTU 4145-2002 over $\mathbb{F}_{2^{257}}$, ECDSA) and parallel 256-bit hashes (GOST 34.311-95, DSTU 7564:2014 Kupyna-256, SHA-256).
100% Post-Quantum Cryptographic Agility (NIST FIPS 204 / FIPS 205): While classical elliptic curves are vulnerable to Shor's algorithm, the 27-channel bijective geometric codec $\mathcal{E}_{10}$ is signature-agnostic — it encodes any 256-bit digest $V = \text{SHA3-256}(\sigma_{\text{PQC}}) \in \{0,1\}^{256}$. Migrating from DSTU 4145-2002 to NIST FIPS 204 (ML-DSA / Dilithium) or NIST FIPS 205 (SLH-DSA / SPHINCS+) requires zero changes to the geometric lattice.
